# 01 - Requirements

## Implementation Status (as of 2026-06-16)

This document is the requirements source of truth. See `docs/02-architecture.md` for what is built vs planned. In brief: REST submission, transactional outbox write, persistence, Kafka dispatch (outbox dispatcher → `application-submitted`), retry/DLQ processing, retention cleanup, and admin replay APIs are implemented. Remaining work: `GET /applications/{id}`, REST endpoint for application-table fallback replay, Testcontainers integration tests, outbox metrics, and CI Avro compatibility checks.

## Overview

This document captures the requirements for a Spring Boot service that accepts application submissions via a REST API, persists them to a database, and publishes an ApplicationSubmitted event to Kafka using a transactional outbox pattern. The system must support event replay and robust retry/failure handling. H2 will be used for initial development with an expectation of future PostgreSQL compatibility.

## Functional Requirements

- API behavior
  - Expose a REST endpoint to submit an application. The endpoint accepts applicant data, validates it, persists a record, and results in an ApplicationSubmitted event being published to Kafka.
  - The API must return a clear success or error response. On success it must return the generated applicationId and correlationId along with the timestamp of creation.

- Input / Output definitions
  - Input DTO (request): must include at minimum:
    - firstName (string)
    - lastName (string)
  - Output DTO (response) on success: must include at minimum:
    - applicationId (unique identifier generated by the service)
    - correlationId (request-scoped id generated by the service)
    - timestamp (creation time)
    - status (e.g., "SUBMITTED" or equivalent)
  - Error responses: must include an error code and human-readable message. Validation failures must return 4xx status codes.

- Data generation rules
  - applicationId must be generated server-side and be globally unique (GUID/UUID or other unique format).
  - correlationId must be generated per request and propagated to persistence, outbox and logs.
  - timestamp must be generated server-side in a well-specified format (ISO-8601, UTC); timezone handling must be explicit.

- Persistence expectations
  - Persist the submitted application record to the local application database before publishing the event (outbox pattern will be used to ensure atomicity between DB write and event publish).
  - The persisted record must contain: applicationId, correlationId, firstName, lastName, timestamp, and event/publication metadata required by the outbox implementation (status, retries, publishedAt, etc.).
  - Support for replay requires keeping the outbox/auditable history of events and/or persisted application state needed for re-emission.

- Event publishing expectations
  - An ApplicationSubmitted event must be produced to Kafka for every successfully persisted submission.
  - Event publishing must be done using a transactional outbox pattern that ensures that the database write and the enqueuing of the outgoing event are coordinated to avoid data loss or duplication.
  - The system must mark events as published (or otherwise update outbox state) only after successful send to Kafka, and must support retrying failed sends.

## Non-Functional Requirements

- Reliability
  - Ensure durability of persisted applications and of outgoing events (no acknowledged submissions are lost).
  - Event publish must be retried on transient failures; permanently failing events must be surfaced to operators and/or moved to a dead-letter mechanism.

- Availability
  - The service should be designed to run in multiple instances; basic correctness must be preserved in concurrent/multi-instance deployments (e.g., outbox processor must be safe for concurrent runners).

- Scalability
  - System must be able to scale horizontally for increased request throughput and increased event publish throughput. Expected throughput and latency targets are TBD (see Open Questions).

- Auditability
  - All submissions and event publication attempts must be auditable: maintain sufficient metadata (timestamps, correlationId, status changes, retries, errors) to debug and to support replays.

- Maintainability
  - Use clear, testable boundaries; produce logs that include correlationId and applicationId for traces.

- Database portability requirements
  - Development environment uses H2.
  - The schema and data-access code must be compatible with PostgreSQL in production with minimal changes (avoid H2-specific SQL features; prefer standard SQL and JPA-compatible constructs).

- Observability
  - Include structured logs (must include correlationId and applicationId), metrics for publishes/failedPublishes/retries, and basic health/readiness endpoints. Tracing is recommended (correlation propagation).

- Security
  - Secrets (DB credentials, Kafka credentials) must NOT be hardcoded and must be loaded from environment/config that is encrypted/secret-managed in production.
  - Authentication/authorization for the REST endpoint is unspecified (see Open Questions).

- Validation
  - Use server-side validation for input fields (non-empty firstName/lastName, length limits). Exact validation rules (length limits, allowed characters) are TBD (see Open Questions).

## Event Requirements

- Kafka topic name(s)
  - Topic name(s) are not finalized. Suggested logical name: `application-submitted` (single topic). See Open Questions for final naming, partitioning and naming conventions.

- Event payload structure (conceptual only)
  - ApplicationSubmitted event (conceptual fields):
    - applicationId (string/UUID)
    - correlationId (string)
    - timestamp (ISO-8601 UTC)
    - firstName (string)
    - lastName (string)
    - optional metadata: source, version, headers (for tracing)
  - The event must be schema-versioned (version field or external schema registry) to allow forward/backward compatibility. Exact schema format (JSON/Avro/Protobuf) is TBD.

- Event lifecycle expectations
  - Produce: one event per successfully persisted application submission.
  - Delivery semantics: at-least-once delivery must be supported. System should either ensure idempotency on consumers or provide deduplication keys (applicationId).
  - Replay: events must be replayable by replaying from the outbox store or by re-publishing from persisted application records. Replay must preserve event ordering where necessary (see Open Questions).
  - Failure handling: transient publish failures must be retried with backoff; permanent failures must be visible and handled via a dead-letter channel or operator intervention.

9. Ordering guarantees
   A: just make sure that events for the same applicationId are published in order. We can achieve this by using applicationId as the partition key.

10. Correlation and tracing
    A: No, use correltionId for all logs and events, and include applicationId in logs.

    A: no metrics or alerting required for this exercise, but we should design the system to allow easy addition of metrics (e.g., publish attempts, failed publishes, retries) and structured logging with correlationId and applicationId.

12. Data retention and cleanup
    A: Outbox published rows will be retained for 3 days for audit and manual replay. An automatic cleanup job will delete outbox records older than 3 days. DLQ records will be retained for 30 days.

13. Database schema details
    A: This will be based on RDBMS vs NoSQL.  If NoSQL we will need query per table. So that would be an application table, Outbox table, dlq table. Make sure tables are indexed appropriately for efficient querying.

Implementation notes & operational recommendations
- Store Avro schemas under `src/main/resources/avro/` with semantic version in file names (e.g., `application-submitted-v1.avsc`). The `avro-maven-plugin` is configured in `pom.xml`; add a CI step to validate Avro schema compatibility before merging (using avro-tools or a Maven plugin).
- Document schema change and compatibility rules in project docs when the process is formalized; include compatibility tests in CI when added.
- Implement the outbox processor as a horizontally-scalable Spring component that atomically marks rows for processing (e.g., update+returning or pessimistic locking) to avoid double-processing across instances.
- Use `scheduled_retry_at` and `attempts` to schedule retries; compute exponential backoff (1s, 2s, 4s) based on attempts.
- Circuit breaker (Resilience4j) applies to **REST API** calls only, not Kafka outbox publishing. Kafka publish failures are handled via outbox retry/backoff and DLQ (see `docs/05-kafka-outbox-design.md`).
- Provide an admin Swagger endpoint to list DLQ items, view details, and trigger replays for individual items.
- Keep published outbox rows for the 3-day retention window to allow operator-driven replays; automatically purge older rows daily.
